# GrantWell v1.5 — Milestone Plan

Two features for the end-user pilot:

1. **Admin NOFO upload visibility** — a clear admin view of which NOFOs were uploaded, processed,
   failed, archived, and made available to users.
2. **Notifications for matching grants** — notify users when a new grant matches their profile,
   agency, or saved criteria.

## Coordination with the re-platform

v1.5 is built on `main` while `grantwell-core` is built in parallel.  Write everything config-friendly (no hardcoded "Massachusetts") so it ports cleanly. Cognito already carries a `custom:state` attribute alongside `custom:role`, so notification matching and recipient pools should be **state-scoped** from the start.

## Why this is achievable — what already exists

The codebase already contains most of the plumbing both features need; the work is assembling and
extending it, not building from zero.

| Need | Already there? | Evidence |
|---|---|---|
| NOFO lifecycle status | ✅ | `status` = `active`/`archived` on the metadata table; live processing stages (as scattered string literals — see note below); review lifecycle (`pending_review`/`approved`/`rejected`/`failed`/`needs_reupload`/`superseded`) |
| Admin review + metrics UI | ✅ | `ProcessingReviewTab`, `ProcessingMetrics`, retry via `reprocess`/`needs-reupload` |
| A clean trigger when a NOFO goes live | ✅ | The pipeline `publish` Lambda flips `status="active"` at a single known line |
| Query "all active NOFOs" for a digest | ✅ | `StatusIndex` GSI (PK `status`, SK `created_at`) |
| API pattern for new endpoints | ✅ | HTTP API + JWT authorizer; `UserManagementClient` is a copy-paste template |
| Scheduled (cron) jobs | ✅ | Existing EventBridge rules (auto-scraper, auto-archive) to copy |
| Enumerate users + emails | ✅ | Cognito `ListUsers` pagination in user-management ([users/index.mjs:96](../lib/chatbot-api/functions/user-management/users/index.mjs#L96), pagination loop at [378-394](../lib/chatbot-api/functions/user-management/users/index.mjs#L378)) |
| **User profile / interests / saved criteria** | ❌ net-new | Cognito carries `custom:role` + `custom:state` only; no profile page, no interests/criteria store |
| **Email sending (SES/SNS)** | ❌ net-new | Zero email infra anywhere in the tree |

So Feature 1 is mostly **assembly of existing parts**; Feature 2 adds two genuinely new things
(a preferences store and email delivery) onto existing hooks that are already in the right place.

## Feature 1 — Admin NOFO upload visibility

**Goal:** one admin view where every NOFO's lifecycle is unambiguous:
**uploaded → processing → failed/quarantined → available to users (active) → archived.**

### Design

The data already exists across two tables; this feature is a **unified lifecycle view** over them,
plus closing three visibility gaps.

- **Lifecycle source of truth:**
  - Live processing stage: `processing_status`, written via `updateProcessingStatus()` in
    [shared/status.mjs](../lib/chatbot-api/functions/nofo-pipeline/shared/status.mjs). ⚠️ `status.mjs`
    is only the *writer* — it does **not** enumerate the stages. The real stage values are hardcoded
    string literals at their call sites: `uploading` ([dispatcher/index.mjs:65](../lib/chatbot-api/functions/nofo-pipeline/dispatcher/index.mjs#L65)),
    `extracting_text` ([extract-text/index.mjs:20](../lib/chatbot-api/functions/nofo-pipeline/extract-text/index.mjs#L20)),
    `synthesizing` ([synthesize/index.mjs:20](../lib/chatbot-api/functions/nofo-pipeline/synthesize/index.mjs#L20)),
    `validating` ([validate/index.mjs:7](../lib/chatbot-api/functions/nofo-pipeline/validate/index.mjs#L7)),
    `quarantined` ([quarantine/index.mjs:25](../lib/chatbot-api/functions/nofo-pipeline/quarantine/index.mjs#L25)),
    `reprocessing` ([reprocess/index.mjs:107](../lib/chatbot-api/functions/nofo-pipeline/reprocess/index.mjs#L107)).
    There is **no** `detecting_sections` stage, and `incomplete` exists only as the quarantine reason
    `incomplete_document`, not a `processing_status`. Task 1 should first centralize these literals
    into a shared constant. Labels in [NOFOsTab.tsx](../lib/user-interface/app/src/pages/dashboard/components/NOFOsTab.tsx).
  - "Available to users": `status = "active"` (vs `"archived"`) on the NOFO metadata table, validated/written in
    [nofo-status/index.mjs](../lib/chatbot-api/functions/landing-page/nofo-status/index.mjs#L127) (~L127-131, validated at L244).
  - Review state (`pending_review`/`approved`/`rejected`/`failed`/`needs_reupload`/`superseded`) — canonical list at
    [admin/index.mjs:376](../lib/chatbot-api/functions/nofo-pipeline/admin/index.mjs#L376),
    [ProcessingReviewTab.tsx](../lib/user-interface/app/src/pages/dashboard/components/ProcessingReviewTab.tsx).
- **Derived lifecycle badge** (frontend): combine the three into one label per NOFO —
  Uploaded · Processing · Failed · Available · Archived — with timestamps (`created_at`,
  `updated_at`) already on the row.

## Feature 2 — Notifications for matching grants

**Goal:** when a new grant matches a user's **profile, agency, or saved criteria**, email them —
real-time on publish, plus a periodic digest. Match dimensions use metadata already captured on
every NOFO: `category`, `grant_type`, `agency`, `status`, `expiration_date`
([nofo-status/index.mjs:127-160](../lib/chatbot-api/functions/landing-page/nofo-status/index.mjs#L127)).
The metadata table also carries a `CategoryIndex` GSI (and a commented-out `AgencyIndex`) usable to
scope match queries.

### Architecture

```
NOFO published (status→active)                     Digest (EventBridge cron)
  publish/index.mjs :110  ──┐                        query StatusIndex status="active"
  (or DynamoDB Stream on    │                        since last run
   metadata table)          ▼                              │
                    match against user prefs  ◄────────────┘
                    (category / agency / saved criteria)
                              │
                    recipient list  ──►  SES send  ──►  user inbox
```

### The three net-new / reused pieces

**2a. Preferences store** (net-new — no profile/criteria model today)
- New DynamoDB table `user-notification-prefs`: PK `userId`, fields `email`, `state`, `categories[]`,
  `agencies[]`, `savedCriteria[]` (named filters), `mode` (`realtime`/`digest`/`off`).
  (Mirror the existing per-user pattern of `FeatureRolloutTable` —
  [tables.ts:112](../lib/chatbot-api/tables/tables.ts#L112).)
- New `/profile` + `/notifications` endpoints following the exact existing pattern: Lambda reading
  `event.requestContext.authorizer.jwt.claims`, wired via `addRoutes(... authorizer: httpAuthorizer)`
  in [index.ts](../lib/chatbot-api/index.ts#L383) (`httpAuthorizer` defined at L116; pattern used 38+ times),
  and a client class mirroring
  [user-management-client.ts](../lib/user-interface/app/src/common/api-client/user-management-client.ts#L10).
- Frontend: a profile/preferences page (net-new) to set interests + saved criteria + mode.

**2b. Matching + triggers** (hooks already in the right place)
- **Real-time:** invoke a `match-and-notify` Lambda right after the publish write at
  [publish/index.mjs:110](../lib/chatbot-api/functions/nofo-pipeline/publish/index.mjs#L110), **or**
  attach a DynamoDB Stream to the metadata table firing when `status` becomes `active` (cleaner —
  also catches admin manual activations). ⚠️ No stream is enabled on `NOFOMetadataTable` today
  ([tables.ts:56](../lib/chatbot-api/tables/tables.ts#L56)); enabling `StreamViewType` is a one-line
  add but may force a table replacement — the publish-hook option avoids that. Match the NOFO's
  `category`/`agency` against prefs.
- **Digest:** an EventBridge cron Lambda (copy the AutoArchive rule at
  [functions.ts:1680](../lib/chatbot-api/functions/functions.ts#L1680); the archive Lambda itself is at
  L1631) that queries `StatusIndex` for NOFOs since last run and batches per user.
- Recipient pool: reuse the Cognito `ListUsers` pagination from
  [users/index.mjs:378](../lib/chatbot-api/functions/user-management/users/index.mjs#L378)
  (helper `listUsers` at [L96](../lib/chatbot-api/functions/user-management/users/index.mjs#L96)),
  scoped by `custom:state`.

**2c. Email delivery** (net-new — no SES anywhere)
- SES: verify sender domain, production access (Early action), IAM `ses:SendEmail` on the Lambda.
- Send Lambda + two templates (real-time match, digest).
