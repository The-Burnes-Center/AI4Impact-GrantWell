## Notes

1. **Testing coverage.** This report combines a full code audit, an axe-core scan (zero violations across all 16 tested page states), an accessibility-tree/keyboard pass, and an NVDA pass with captured speech output covering all nine user-reachable pages of the running application plus deep states.
2. **Scope**: the deployed web frontend, both the unauthenticated marketing/landing/login pages and the authenticated application (home, requirements checklist, chat, document editor, sessions, admin dashboard). Out of scope: PDF/DOCX exports generated via jsPDF/docx, email content sent by Cognito, and AWS-hosted backend services.
3. **Content-dependent caveat**: NOFO summaries and AI chat responses render author/AI-supplied markdown; conformance of that dynamic content (e.g., link text quality, language of parts) depends on the content itself.
4. WCAG 2.2 removed Success Criterion 4.1.1 Parsing; it is intentionally absent from Table 1.
5. One finding was also a functional product bug affecting all users equally: the toast-notification system (`NotificationProvider`/`NotificationBar`) was only mounted in the unused `layouts/BaseAppLayout.tsx`, so all chat and dashboard toast notifications were silently dropped. **Remediated 2026-07-10** — the providers are now mounted at the app root and the fix was verified live. **2026-08-11**: the dead `layouts/BaseAppLayout.tsx` has now been deleted so the duplicate mount cannot be re-wired. It had survived the July 10 fix because `layouts/ChatLayout.tsx` exports its own default function *also* named `BaseAppLayout`, which is what `PlaygroundPage` actually imports — a name collision that made the dead file appear referenced. Confirmed unreferenced before removal (sole `layouts/` import points at `ChatLayout`; no barrel file; `tsc --noEmit` and a full production build both pass after deletion).
6. **Remediation status**: every item in the Remediation Priorities list below was applied to the source tree on July 10, 2026 and re-verified against a local build (9/9 automated checks passed: keyboard grant selection end-to-end, notification announcement, focus visibility, input-border contrast, login title, and clean axe re-scans of home and dashboard). **Correction to the July 10 edition**, which stated the fixes were "not yet deployed": they have since shipped. Verified live in the production bundles at grantwell.us on August 11, 2026 — keyboard-operable grant rows (`tabIndex`/`onKeyDown` present in the HomePage chunk), the notification system mounted at the app root, the remediated colour tokens (`#B45309`, `#047857`, `#6b7280`, `#767676`, `#CD0D0D`) present and the failing ones (`#24A850`, `#9ca3af`, `#e74c3c`, `#d7dee8`) absent, the 30-second voice cutoff removed, and the dashboard auto-refresh pause control present. Note that partner-state snapshots cut before tag `v0.1.0` (July 16, 2026) do **not** contain these fixes.

7. **Second remediation round, August 11, 2026.** An external accessibility review from a partner state reported findings matching this report's pre-July-10 state. Reconciling them against the live build established that two of the four reported blockers were already fixed and live, and two were only *partially* fixed: the specific elements named in the July 10 round were remediated, but other elements exhibiting the same defect were still live and correctly reported. A systematic sweep (method 5 above) then found ten residual defects across five criteria, and an independent verification pass found three more (see edition 1.2) — all fixed and verified in the built output on August 11, 2026. The July 10 edition's per-criterion "Supports" ratings were therefore optimistic for 1.3.1, 1.4.3, 1.4.11, 2.4.7, and 2.5.8; the remarks for those criteria now record what the second round found.

    The root cause was process, not code. Two failures compounded: single-instance fixes were applied without sweeping for sibling instances, and the repository had **no automated accessibility gate** — CI ran neither lint nor tests, and the axe/NVDA tooling described in methods 2-4 left no committed, reproducible artifacts, so no assertion in this report could be independently re-verified. Both are now addressed. An accessibility regression suite is committed to the repository: component-level tests targeting each defect that recurred (keyboard-operable grant rows, dialog labelling and unique ids, and the notification system actually rendering rather than merely being invoked), and `@axe-core/playwright` page scans of the unauthenticated states, wired into a `quality` job that gates deployment in both workflows. Each component assertion was validated against the pre-fix code to confirm it fails when the defect is present. Coverage boundary, stated plainly: authenticated page states require live credentials and a running backend, so they are scanned on demand rather than in CI, and component-level colour-contrast checks are disabled because a headless DOM does no painting — page-level axe covers contrast instead.

## Automated and Live Testing Results

Conducted July 10, 2026 against a local build (`vite dev`) connected to the staging backend (grantwell.us environment), using a temporary admin/developer test account (created for the scan, deleted afterward). axe-core with the `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa` rule tags.

**axe-core: 0 violations in all 16 tested page states** — landing, login, home (empty and with a grant selected), requirements checklist, chat playground (auto-opened help dialog, empty session, and a live conversation with a streamed AI reply), chat sessions, document-editor drafts, document editor, and the four admin dashboard tabs (Grants, Processing Review, User Management, Feature Rollouts). 42 "incomplete" color-contrast items on the home hero (axe could not compute backgrounds behind decorative pseudo-elements) were manually verified as passing (dark #282828-family text on light backgrounds, > 7:1).

Live confirmations of code-review findings:

- **Grant rows unreachable by keyboard (2.1.1 blocker)** — a full tab-walk of the home page goes from the sort-header buttons directly to pagination; no grant row ever receives focus.
- **Notifications never appear (4.1.3)** — clicking the dashboard's Refresh button (whose code calls `addNotification("success", "Dashboard refreshed successfully")`) produced zero `role="alert"`/`role="status"` elements and zero toast DOM nodes.
- **Send/Stop focus invisible (2.4.7)** — with keyboard focus on the chat Send button (and on Stop during streaming), computed styles show `outline: none` and no box-shadow.
- Working as intended: sign-in flow fully keyboard operable; help-dialog focus trap cycles correctly and releases on close; skip links and landmark structure exposed as designed; chat streaming announces via `role="status"` ("Assistant is replying") and a `role="log"` message stream with per-message `<article>` elements and sr-only "You said:"/"Assistant replied:" prefixes; sources disclosure and Stop button appear/disappear correctly around the stream.

**NVDA pass** (NVDA + Microsoft Edge on Windows 11, automation via Guidepup with captured speech; July 10, 2026). All nine user-reachable pages were read with NVDA. What NVDA actually announced:

- *Sign-in page*: form landmark and "Sign in" region; "Email address — edit, required"; "Password — edit, protected, required"; "Show password — check box, not checked"; sign-in/sign-up mode announced as "Authentication mode, grouping, toggle button, pressed"; all buttons named. Credentials could be pasted (no paste blocking) and sign-in was completed entirely through NVDA — supporting 3.3.2, 3.3.8, and 1.3.1 for the auth flow.
- *Landing page*: correct heading outline (level 1 wordmark, level 2 feature sections), labelled navigation/complementary/content-info landmarks, "Skip to main content" link, "(opens in new tab)" announced on partner links.
- *Authenticated home*: h1 announced; the authoring-provided screen-reader orientation note is read; search box announced with label and hint; filter combo boxes announced with labels and values; the div-based grid announced as "table, with 11 rows and 5 columns, Grants" with header-row sort buttons — the ARIA table semantics work in a real screen reader.
- *Home tab-walk*: focus went search → filters → sort buttons → pagination → "Go to Admin Dashboard"; **NVDA never landed on a grant row**, re-confirming the 2.1.1 blocker with real AT.
- *Requirements checklist*: "Requirements navigation" sidebar landmark, h1 "Application Requirements for [NOFO name]", Help button, tabs announced as "tab, selected, ELIGIBILITY".
- *Chat playground (live conversation)*: h1 with the NOFO name; "Grant Well assistant chat, region, list"; the assistant's message read with its sr-only "Assistant replied:" prefix; "Copy message to clipboard" button; "Message the Grant Well assistant" input announced as "edit, multi line"; voice input announced as "toggle button, not pressed, Start voice input".
- *Chat sessions*: sidebar navigation buttons, breadcrumb with "current page, Sessions" (`aria-current`), h1, disabled Delete announced as "unavailable", sessions grid announced as a table.
- *Document editor*: welcome modal content readable (heading levels, step list, "GET STARTED"); wizard step 1 announces the ProgressStepper correctly — "button, current step, Step 1: Project Basics (current)" with future steps "unavailable" (`aria-current="step"` and disabled states verified in real AT).
- *Drafts*: breadcrumb "list, with 2 items … current page, Drafts", h1, "Create new draft" button.
- *Admin dashboard*: h1 "Admin Dashboard", "Grants tab selected" (tab semantics), and a refreshing control announced as "button, unavailable, busy, Refresh dashboard" (`aria-busy` voiced).

Limitations: the staging Processing Review queue was empty ("No NOFOs pending review"), so the quality-score contrast failures (1.4.3) could not be exercised live — the computed ratios from CSS stand as evidence. The maintenance page renders only during maintenance mode and was reviewed in code only. Delete-confirmation and document-upload dialogs, wizard steps 2-5, and the dashboard's non-default tabs were evaluated in code and via the axe/accessibility-tree pass, but not read with NVDA.

## Terms

The terms used in the Conformance Level information are defined as follows:

- **Supports**: The functionality of the product has at least one method that meets the criterion without known defects or meets with equivalent facilitation.
- **Partially Supports**: Some functionality of the product does not meet the criterion.
- **Does Not Support**: The majority of product functionality does not meet the criterion.
- **Not Applicable**: The criterion is not relevant to the product.
